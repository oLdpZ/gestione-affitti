## Goal
Trasferire i dati esistenti dal blob `dati_utente.blob_json` alle nuove tabelle per-entity in modo **idempotente** e **all-or-nothing** (PL/pgSQL function dentro singola transazione). Pre-backup automatico via snapshot ring + download JSON. Modal "Migrazione fallita" con bottone esporta JSON di emergenza. Toggle `usaNuovoSchema` in Salute dati. Widget Salute dati estesi (queue count, last pull/push, conflitti aperti, storage IDB, bottone flush manuale).

## Context summary
- PL/pgSQL function `migrate_blob_to_entities(blob jsonb)` — verbatim da RESEARCH §7. `language plpgsql` garantisce transazione singola: qualsiasi `raise exception` rollbacka tutto.
- Idempotency check client-side: `if blob is null OR new tables non-empty for user → return`. RPC server-side ulteriore safe via `on conflict (id) do nothing`.
- Pre-migration safety: `pushSnapshot()` + `esportaJSON()` (download auto) — riusa codice PR1.
- Partial fail → modal blocking "Migrazione fallita, scarica backup" con bottone "Esporta JSON di emergenza" (riusa `esportaJSON()`).
- Rollback flag `localStorage.usaNuovoSchema = false`: toggle in Salute dati "Avanzato".
- Salute dati estensione (REQ-SAFE-05 extension): mutation queue count, lastPullAt/lastPushAt, count conflitti aperti, storage IDB stimato, bottone "Flush coda manuale".

    2. **Helper `migraBlobAPerEntita()`** aggiunto come metodo:
       ```js
       async migraBlobAPerEntita() {
         if (!this.utente) return;
         if (this.migrazioneInCorso) return;
         this.migrazioneInCorso = true;
         try {
           // 1. Idempotency check: blob non-null AND new tables empty?
           const { data: blobRow } = await sb.from('dati_utente').select('blob_json').eq('user_id', this.utente.id).maybeSingle();
           if (!blobRow?.blob_json || !blobRow.blob_json.proprieta) {
             return; // niente da migrare
           }
           const { count: pCount } = await sb.from('proprieta').select('id', { count: 'exact', head: true });
           if (pCount && pCount > 0) {
             return; // già migrato (idempotent no-op)
           }

           // 2. Pre-migration safety: snapshot ring + auto JSON download
           try {
             this.pushSnapshot(this._lastSnapshotData || JSON.parse(JSON.stringify(this.dati)));
             this.esportaJSON();
           } catch (e) {
             this.pushErrore({ message: 'pre-migration backup: ' + (e?.message || 'unknown'), severity: 'warn' });
             // non-blocking — continua comunque
           }

           // 3. RPC atomica server-side
           const { error } = await sb.rpc('migrate_blob_to_entities', { blob: blobRow.blob_json });
           if (error) {
             this.modalitaMigrazioneFallita = true;
             this.pushErrore({ message: 'migrate_blob: ' + error.message, severity: 'error' });
             return;
           }

           // 4. Success → ricarica via RPC nuova
           const { data, error: rErr } = await sb.rpc('get_user_data');
           if (!rErr && data) {
             this.dati = this.adattaShape(data);
             this.lastPullAt = new Date().toISOString();
             this._lastSnapshotData = JSON.parse(JSON.stringify(this.dati));
             this.mostraToast('successo', 'Migrazione completata');
           }
         } finally {
           this.migrazioneInCorso = false;
         }
       },
       ```

    3. **Wiring in `caricaDatiUtente()`** (modifica T-05-01-03 result): nel branch `usaNuovoSchema` quando RPC ritorna `data.proprieta.length === 0`, **invece di fall-through immediato a blob path**, prima chiamare `await this.migraBlobAPerEntita(); const { data: r2 } = await sb.rpc('get_user_data'); if (r2 && r2.proprieta && r2.proprieta.length > 0) { this.dati = this.adattaShape(r2); return; }`. ## Threat model
- **Migration race condition multi-tab (2 tab simultanei)**: pre-check `pCount > 0` può ritornare 0 per entrambi → entrambi chiamano RPC → secondo RPC vede tabelle popolate dal primo (data ha già processato `on conflict do nothing`) → secondo è no-op-ish ma può fare download backup duplicato. **Mitigation accettata**: backup duplicato non corrompe nulla; download ridondante è fastidio minore. Per fix robusto: advisory lock Postgres `pg_advisory_xact_lock(hashtext('migrate-'||uid::text))` — DEFERRED a iterazione futura se manifesta.
- **PL/pgSQL atomicity**: any `raise exception` dentro la function rollbacka tutta la transazione. Verificato in T-05-03-05 step 4 (partial-fail simulation con FK orfana → rollback → tabelle vuote post-fail). Confermato in RESEARCH §7 falsification.
- **Emergency JSON contains sensitive data**: il file scaricato contiene tutti gli incassi e dati personali inquilini. **Mitigation**: filename con timestamp, non auto-uploaded da nessuna parte; utente è ownership-aware. Documentato; no encryption necessaria (out of scope, vedi deferred).
- **Cross-user IDB residuo**: clear di `mutationQueue` in `logout()` (T-05-03-02 step 4) chiude il vettore di "user B applies user A's pending mutations".

## Risks & mitigations
- **R1 (CEO) — Migrazione rompe dati**: mitigato in cascata: PL/pgSQL atomic + pre-snapshot + auto JSON + dual-write 2 settimane + rollback flag in UI.
- **R-NEW-5 (RPC timeout)**: family-tier ~600 rows = ~200ms RPC. Statement timeout 8s default Supabase free → margine 40×. Se utente avesse 50k rows, chunk via cursor — deferred.
- **Backup non scaricato per browser blocker**: `esportaJSON` usa `Blob` + `URL.createObjectURL` + click programmatico — Chrome può silenziosamente bloccare se popup blocker aggressivo. **Mitigation**: snapshot ring di PR1 funge da pre-migration backup secondario (always-in-localStorage, no browser permission required).
