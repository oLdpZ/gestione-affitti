## Goal
Esporre all'utente le 3 nuove entità: (1) CRUD inquilini in Impostazioni + quick-add in scheda proprietà; (2) CRUD tipi_utenza in Impostazioni con seed `acqua`/`luce`/`gas`; (3) field `scadenzaGiorno` (1-31 o `fine_mese`) in form proprietà con calendario raggruppato per scadenza. Retrofittare i form esistenti (incasso, utenza, banca) per `enqueueMutation` per-entity nello stesso commit (DEC-013).

## Context summary
- Inquilini: campi `nome` (required), `codice_fiscale` (16 char check), `telefono`, `email` (regex opzionale), `proprieta_id` (select). Soft-delete + cestino esteso (REQ-SAFE-01-02 da PR1 — riusa pattern).
- Tipi_utenza: CRUD list; seed iniziale `acqua`/`luce`/`gas` migrati dal codice; aggiunta runtime (es. "rifiuti") appare immediatamente nei dropdown utenza (Alpine reactivity nativo).
- Hard-delete tipo_utenza BLOCCATO se ci sono utenze associate (FK `on delete restrict` lato DB + pre-check applicativo + toast "Tipo utilizzato").
- `scadenzaGiorno`: select dropdown 1-31 + opzione "Fine mese"; default `'1'` per backward-compat con generaIncassiAttesi attuale.
- `gruppiCalendario` (app.js ~riga 1080+) ora raggruppa dinamicamente per `scadenzaGiorno` invece di hardcoded 1/15/fine_mese.
- Form utenza dropdown: hardcoded `<option value="acqua">...` → `<template x-for="t in dati.tipi_utenza">`.
- `resetFormUtenza`: `tipo: 'acqua'` → `tipo_id: <dati.tipi_utenza[0]?.id>`.

    3. **CRUD metodi (save/edit)**:
       ```js
       resetFormInquilino() {
         this.formInquilino = { id: '', nome: '', codiceFiscale: '', telefono: '', email: '', proprietaId: '' };
         this.formInquilinoVisibile = false;
       },

       apriFormInquilino(esistente = null) {
         if (esistente) {
           this.formInquilino = { ...esistente };
         } else {
           this.resetFormInquilino();
           this.formInquilino.id = crypto.randomUUID();
         }
         this.formInquilinoVisibile = true;
       },

       async salvaInquilino() {
         const inq = this.formInquilino;
         if (!inq.nome) { this.mostraToast('warn', 'Nome obbligatorio'); return; }
         if (!this._validaCodiceFiscale(inq.codiceFiscale)) {
           this.mostraToast('warn', 'Codice fiscale deve essere 16 caratteri alfanumerici maiuscoli'); return;
         }
         if (!this._validaEmail(inq.email)) {
           this.mostraToast('warn', 'Email non valida'); return;
         }
         const esistente = (this.dati.inquilini || []).find(i => i.id === inq.id);
         if (esistente) {
           Object.assign(esistente, inq);
         } else {
           if (!this.dati.inquilini) this.dati.inquilini = [];
           this.dati.inquilini.push({ ...inq });
         }
         if (this.usaNuovoSchema) {
           const camelPayload = {
             id: inq.id, userId: this.utente.id, proprietaId: inq.proprietaId || null,
             nome: inq.nome, codiceFiscale: inq.codiceFiscale || null,
             telefono: inq.telefono || null, email: inq.email || null,
           };
           await this.enqueueMutation(esistente ? 'update' : 'insert', 'inquilini', inq.id, toDb(camelPayload), inq._serverUpdatedAt || null);
         }
         await this.salva();
         this.resetFormInquilino();
       },
       ```

## Threat model
- **Hard-delete tipo_utenza con utenze associate**: bloccato lato client (`usatoDaUtenza` pre-check + disabled button) E lato DB (FK `on delete restrict`). Doppia barriera. Toast italiano fornisce contesto.
- **Codice fiscale validation**: solo lunghezza 16 char (no checksum). Sufficiente per uso family-tier; checksum vero CF è out-of-scope (richiederebbe ~50 LOC algoritmo). Email regex permissiva (no DNS check, by design).
- **PII inquilini in IDB locale**: codice fiscale + telefono + email finiscono in IndexedDB se utente è offline al momento del save. **Mitigation accettata**: il device è dell'utente, PII è dei suoi inquilini (relazione owner-known); no encryption layer aggiunto.
- **Multi-tab tipi_utenza race**: 2 tab aggiungono "rifiuti" simultaneamente → 2 enqueue insert con stesso `nome` → secondo fallisce con unique constraint `(user_id, nome)`. Catch in flushMutationQueue: status 23505 (Postgres unique violation) non è 409 né 5xx → cade nel `pushErrore + break` branch. **Mitigation**: utente vede entry stuck in coda + toast errore; manual flush retry no-op. Acceptable per ora; future: trattare 23505 come "already done, drop from queue".

## Risks & mitigations
- **Migration di utenze legacy a `tipo_id`**: la PL/pgSQL function (plan 05-03) mappa string `tipo` → `tipo_id` via case statement. Edge case: utenza con `tipo` custom non in (acqua|luce|gas) → fallback safe a `acqua` con warning loggato (RESEARCH §7). Post-migration l'utente può rinominare/aggiungere tipi e correggere manualmente.
- **`gruppiCalendario` performance**: se proprietà = 50 e scadenzaGiorno distinti = 10, sort N log N trascurabile.
- **Form inquilino senza proprietà**: `proprieta_id` nullable lato DB; UI permette "Nessuna proprietà". Utile per inquilini in transito.
